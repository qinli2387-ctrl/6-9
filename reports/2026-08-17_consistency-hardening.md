# D1 写入一致性加固报告

日期：2026-08-17

## 基线

- 每日任务 API 先读取状态，再分别更新任务、学习事件和 XP；两个并发请求可能都按旧状态奖励 XP。
- 词卡 API 先读取旧 FSRS 状态，再分别更新词卡、复习日志和学习事件；同一词卡的并发请求可能重复消费旧状态。
- 目标设置先保存 profile，再查询并创建第一关，两个写入不属于同一原子操作。

## 依据

- Cloudflare 官方 D1 文档说明 `D1Database.batch()` 按顺序执行语句，批次中任一语句失败会中止或回滚整个序列：[D1 Database batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)。
- Drizzle D1 驱动提供 `db.batch()`，本项目同时使用底层 `db.$client.batch()` 构造带条件的原子 SQL。

## 变化

- 新增 `lib/task-completion.ts`：在一个 D1 批次中按旧任务状态条件更新 XP、写学习事件并完成任务。
- 词卡调度以 `id + user_id + reps + last_review_at` 作为乐观版本；复习日志、可选学习事件和词卡状态在同一 D1 批次写入。
- 已过期的词卡请求返回 409；并发竞争失败也返回 409，不再重复写日志。
- 词汇队列完成时复用原子任务完成函数，避免并发完成词汇任务时重复奖励 XP。
- 目标设置的 profile upsert 与第一关幂等创建改为 Drizzle D1 batch。
- 本地集成脚本增加每日任务和词卡的真实并发请求。

## 已验证

- 每日任务两个并发完成请求：HTTP 均为 200，`xpEarned` 合计 10，profile XP 仅增加 10，学习事件恰好一条。
- 同一词卡两个并发复习请求：一个 200、一个 409；`vocab_reviews` 与 `study_events` 各一条。
- 顺序重复完成同一任务：返回 200、`xpEarned` 为 0。
- `pnpm test:app:local`：通过完整三周流程、并发、失败路径和跨用户隔离。
- `pnpm check`：类型检查、ESLint、真实 D1 迁移验证、Vinext 五阶段构建和 11/11 自动测试通过。
- 浏览器回归：1280×800 与 390×844 正式复习页无横向溢出，四个选项正常，无控制台错误或警告。

## 失败与处理

- 浏览器首次导航在规定时间内超时，但页面随后正常完成加载；复用同一标签读取 DOM 后，桌面和手机回归均通过。没有切换浏览器或隐藏该超时。

## 安全与数据一致性

- 所有条件更新均同时包含认证 `userId` 和资源 ID。
- 词卡版本条件阻止旧页面或并发请求覆盖更新后的 FSRS 状态。
- D1 batch 保证本轮覆盖的语句组在 SQL 错误时整体回滚。
- 未执行生产迁移、远端数据修改或 Sites 发布。

## 独立审查发现

- 本轮实现解决的是“每日任务”和“单张词卡”的原子边界。
- 定位测试仍依次写错题、baseline 和事件；五题动态关卡仍可能跨多个批次更新错题/词卡、关卡状态、事件和 XP。
- 因此全请求故障注入仍列为 P2，未将局部原子性描述为全系统事务化。

## 下一步

1. 为定位测试建立一次性 attempt/idempotency 记录并把相关写入合并为一个批次。
2. 为整关提交增加 attempt 状态机或可恢复写入流程，覆盖五个复习来源和 XP。
3. 恢复正式 Sites/D1 后做两设备并发与重试验收。
